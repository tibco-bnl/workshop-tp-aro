## What is new

### Control Plane

- **Infrastructure resource customization:** CPU, memory, and storage of infrastructure components on Kubernetes and Control Tower Data Planes can be overridden with a YAML editor on the Data Plane configuration page.
- **On-demand infrastructure components (Control Tower):** a Control Tower Data Plane provisions only the baseline infrastructure components automatically. Components such as the Hawk Console, BW Adapter, and MFT adapter are installed when your active capabilities require them, or later from the Data Plane configuration page.
- **Application Operator permission:** users can start, stop, restart, and scale applications and configure their environment variables, but cannot delete applications. The permission can be scoped to a namespace within a Data Plane.
- **Application log download:** history logs can be downloaded as plain text or CSV (matching the time range and filters in the History Logs viewer), and real-time logs as text, directly from the Control Plane UI without access to the log server.
- **TESSA:** model calls can run on Amazon Bedrock in your own AWS account as an alternative to a customer-provided OpenAI API key, and TESSA can interact with the EMS capability through an EMS MCP server.

### Capabilities

- **BusinessWorks 6 Containers:** new alert categories **Instance Count** and **App Status**; the Application Operator permission is supported (including namespace-scoped users). Deploying, upgrading, deleting, and auto-scaling are not allowed for that permission.
- **BusinessWorks 5 Containers:** process diagrams get Zoom In, Zoom Out, and Reset controls; new **Instance Count** and **App Status** alert categories; Application Operator permission support; a new API under API Docs exposes a few actionable Hawk methods that were previously available through `/commands` on port 8090.
- **BusinessWorks 5 / Adapters on Control Tower:** the RESTful APIs under `/cp/bw5/v1/ct` cover applications, domains, machines, monitoring, installed software, plugins, and rulebases, and are available in Swagger UI, the CLI, and the BusinessWorks MCP Server, which now provides read-only tools for BW5 on-premise applications managed through Control Tower.
- **Flogo:** engine variables can use the **password** type (value masked in the UI); `build-tp-deployment` in the Flogo App Build CLI can include connector supplements in the generated `build.zip`.

### Removed

- **NGINX Ingress Controller:** because the community has ended active development, its usage is removed from TIBCO Operated Control Plane. Customers may continue to use it in their own deployments, but TIBCO no longer officially supports or recommends it with Control Plane and Data Planes. On ARO the OpenShift Router remains the supported ingress path.

## ARO requirements and operator notes

- The 1.22 system requirements identify CNCF-certified Kubernetes and certify Kubernetes 1.35 (unchanged from 1.21). Confirm the supported OpenShift/ARO release for your environment with the current TIBCO requirements before choosing a cluster version.
- The official requirements list PostgreSQL 16 with `uuid-ossp` for self-hosted Control Plane and Helm 3.17.0 or later.
- The OpenShift Router (`ocp-v4.0`) is listed for Control Plane and, as the default ingress controller, for OpenShift Data Planes. Preserve the existing `tp-scc` service-account grants required by the ARO workshop and follow the generated Data Plane commands when registering a cluster.
- The `tibco-cp-base` 1.22.0 chart adds `global.tibco.monitoringServiceCompatAlias` (default `true`), which creates a `tp-cp-monitoring-service` Service forwarding port 7831 to the orchestrator management server on 8833. Per the chart's values comments, set it to `false` only if you enable the monitoring-service rollback net, which creates a Service with the same name.
- For custom image registries, follow the cluster registration flow for Kubernetes Secret authentication (introduced in 1.21) and create the secret in each applicable Data Plane namespace.
- For air-gapped or private-registry deployments, use the matching 1.22.0 image manifests and official image-sync scripts; push updated images before starting the upgrade.

## Upgrade from 1.21.0

The official upgrade assistant requires a deployed Control Plane at `app_version` 1.21.0. Do not use it to skip a minor release.

1. Back up the database, Helm values, and required Kubernetes secrets. Record `helm history`, confirm the ARO `tp-scc` grants, and verify the Control Plane release is healthy.
2. If using a custom image registry, mirror the 1.22.0 images before upgrading. Run the official prerequisite validation script and `helm repo update`.
3. Use [`scripts/1.22.0/upgrade.sh`](https://github.com/TIBCOSoftware/tp-helm-charts/blob/main/scripts/1.22.0/upgrade.sh) and its README. The assistant checks the existing release is deployed at 1.21.0, generates versioned values or runs the `tibco-cp-base` upgrade to 1.22.0, and verifies the result. Alternatively, run the documented `helm upgrade` of `tibco-cp-base` with `--version=1.22.0` against your current values.
4. The assistant migrates the `tp-cp-o11y` settings: in 1.22.0, `tp-cp-o11y.capabilities.o11y.default` and `.withResources` are merged into `tp-cp-o11y.capabilities.o11y`. If either old section exists, it sets `overwriteRecipe` from the old `default.overwriteRecipe` (`"false"` if unset), removes both old sections, and drops other keys in them so the 1.22.0 chart defaults apply. All other values are unchanged; review them yourself.
5. Upgrade the decoupled capability charts after the Control Plane. Use the exact versions in the `control-plane`, `bw`, `flogo`, `developer-hub`, `hawk`, `messaging`, `mcp-hub`, and `be` artifact files.
6. Upgrade Data Plane infrastructure and capabilities from the Control Plane UI, and upgrade the capabilities after the infrastructure. Verify the generated commands and selected hybrid connectivity/controller options, and validate SCC grants for any new service accounts.
7. Confirm Control Plane and Data Plane workloads are healthy and validate installed chart versions against the artifact manifests.
8. Optional: if any Data Plane had Resources configured before the upgrade, the stale `o11y-exporter.yaml` recipe remains on the Control Plane PVC at `/private/tsc/config/capabilities/platform/`. Nothing reads it, so it is harmless; the official upgrade page documents how to remove it (run `kubectl exec` in a pod that mounts `tsc/config`, such as the orchestrator pod, not the `o11y-service` pod).

The assistant requires Bash 4+, yq 4.45.4+, Helm 3.17+ and jq 1.8+ for Helm flows, and kubectl for post-upgrade checks. If `manageDbSchema` is false, follow the official external PostgreSQL schema-management procedure. Do not change the default registry or chart repository during this upgrade.

From 1.20.0 or earlier, upgrade through 1.21.0 first using the [1.21.0](./v1.21.0) guidance (and [1.20.0](./v1.20.0) / [1.19.0](./v1.19.0) before it).

## Known issues to review

- **PCP-26766:** after you customize the observability environment values in the recipe customization UI and then update the observability resource configuration, the customized values are reset to defaults in the UI and at runtime. No workaround.
- **PCP-25998:** after upgrading the Control Plane from 1.21 to 1.22, downloading real-time or history logs fails with "404 page not found" for applications on an existing Data Plane that has not been upgraded. Newly registered Data Planes are not affected. Workaround: upgrade the Data Plane to 1.22, including its observability capability.
- **PCP-27651 (BW6 Containers):** after upgrading Data Plane infrastructure components to 1.22.0, the Capability Provisioner and the application pod Fluent Bit sidecar show error logs. No workaround is documented.
- **PCP-9344:** if only infrastructure components are upgraded and capabilities are not, existing apps can lose endpoints, monitoring data, and environment-control values. Upgrade the capabilities after the infrastructure.
- **PCP-20136:** the documented cleanup workaround applies only to Control Tower Data Planes configured with the NGINX Ingress Controller. ARO deployments should review the official issue conditions before applying it.

The 1.21.0 known issues PCP-24968, PCP-24894, and PCP-24555 do not appear on the 1.22.0 known-issues page.

Review the full [official 1.22.0 known-issues list](https://docs.tibco.com/pub/platform-cp/1.22.0/doc/html/Release-Notes/known-issues.htm) before production changes.
